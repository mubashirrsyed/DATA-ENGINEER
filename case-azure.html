01AZURE · INGESTION FRAMEWORK

Metadata-Driven Incremental Data Platform

A reusable ingestion framework that onboards new source tables through configuration rather than new pipelines, and loads only what changed since the last successful run.

ROLEData Engineer
PLATFORMAzure Data Factory · ADLS Gen2

THE PROBLEM

One pipeline per table does not scale.

The conventional approach to ingestion is to build a pipeline per source table. Each new table means new artefacts to author, test, deploy and monitor. At a dozen tables it is tedious; at fifty it becomes the main cost of the platform, and every change to load behaviour has to be applied in fifty places.

The second problem is reload cost. A full extract on every run is simple to write but grows linearly with table size, and it silently hides a correctness risk: if a run fails halfway, there is no reliable record of what was actually processed.

ENGINEERING DECISIONS

What was chosen, and why.

Configuration over duplication

Datasets and linked services are fully parameterised, so the source table, schema, target path and load mode all arrive as runtime values. Onboarding a table becomes a row in the control table.

→ New sources ship without a deployment.

Watermark as the unit of truth

A control table holds the last successfully processed timestamp per table. Each run reads it, filters the source above it, and only advances it after the load is validated.

→ A failed run is safe to retry.

Stored procedures for state changes

Watermark reads and updates are wrapped in stored procedures rather than inline activity expressions, keeping the transition logic in one auditable place.

→ Load state is testable in isolation.

Secrets outside the pipeline

Every credential resolves through Azure Key Vault at runtime; no connection detail lives in a pipeline definition or repository.

→ Rotation never touches the pipeline.
