Medallion Lakehouse & Dimensional Serving

A governed transformation layer that turns raw operational extracts into standardised Silver tables and a maintainable Gold dimensional model that reporting teams can depend on.

ROLEData Engineer
PLATFORMAzure Databricks · Delta Lake
PATTERNMedallion + star schema
CONTEXTEpsilon · 2022–2025

THE PROBLEM

Reporting was coupled to source system keys.

Raw operational data arrived denormalised and inconsistently typed, with the same business concept spelled differently across extracts. Reports were built directly on top of it, which meant every downstream query carried its own cleaning logic and every source change broke something.

The deeper issue was key coupling. Analytical models referenced source primary keys directly, so a system migration or a re-keying on the source side would have invalidated history that had already been reported on.

How it fits together.

ENGINEERING DECISIONS

What was chosen, and why.

Bronze stays immutable

Raw data is never edited in place. Every correction happens downstream, so the landed record remains an auditable account of what the source actually sent.

→ Any transformation can be replayed.

Surrogate keys in Gold

A denormalised dataset was decomposed into fact and dimension tables, each dimension carrying a generated surrogate key rather than the source identifier.

→ Source re-keying no longer breaks history.

SCD Type 1 through Delta MERGE

Dimension upserts run as a single MERGE per incremental batch, matching on business key and updating in place, rather than as a delete-and-insert cycle.

→ Dimensions converge without reconciliation.

Governance at the layer boundary

Unity Catalog defines access per layer, so analysts reach Gold while raw and intermediate data stay restricted, with lineage and audit available across all three.

→ Access reflects data sensitivity.
