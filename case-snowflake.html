04SNOWFLAKE · ELT PLATFORM

Azure-to-Snowflake Processing Platform

A controlled Azure-to-Snowflake design for relational and Parquet data, with automated loads, incremental processing, deliberate compute management and real recovery options.

ROLEData Engineer
PLATFORMSnowflake · Azure Data Factory
PATTERNAutomated ELT + cost control
CONTEXTDreamcare Developers · 2020–2022

THE PROBLEM

Compute was always on, and failures were manual.

Data had to move from Azure into Snowflake across two quite different shapes — relational tables and Parquet files — and each was being handled as its own bespoke process. When a load failed, recovery meant someone deciding by hand what to rerun and hoping the boundary was right.

Cost was the second pressure. Warehouses sized for the heaviest job ran continuously regardless of workload, so idle time was billed at peak capacity.

How it fits together.

ENGINEERING DECISIONS

What was chosen, and why.

One path for two data shapes

Relational extracts and Parquet files converge on the same external stage and COPY INTO pattern, rather than each keeping a separate bespoke route into Snowflake.

→ Half as many things to operate.

Streams and Tasks over schedules

Change detection uses Streams, with Tasks reacting to what actually arrived instead of firing on a clock and hoping data is present.

→ Processing follows data, not time.

Warehouses sized to workload

Virtual warehouses were right-sized per workload with auto-suspend and auto-resume, so compute stops when queries do.

→ Idle capacity stops being billed.

Recovery without re-ingestion

Time Travel covers accidental changes and zero-copy cloning creates full-size test environments instantly, so testing and recovery never touch the source system.

→ Mistakes are reversible in place.
